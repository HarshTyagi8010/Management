## Batch B Prerequisites and Architectural Safeguards (Phase 10)

1. **Canonical `recordKind` Values**:
   - Verified in implementation (`payments.ts`, `notes.ts`, `statements.ts`): Standard payment records use `recordKind: 'payment'` (not `'standard'`). Excess credits created from notes use `recordKind: 'credit_note_excess'` (customer) and `recordKind: 'debit_note_excess'` (supplier).
2. **Double-Counting Prevention**:
   - Note-origin excess credits must remain excluded from gross statement totals (as implemented in `statements.ts` via `$ne: 'credit_note_excess'`) to prevent counting the liability/asset both in the originating note and in the synthetic settlement record.
3. **Signed AR/AP Bridges**:
   - Must be mapped strictly from actual double-entry journal lines (debit/credit rules in `packages/domain/src/journal.ts`) rather than display heuristics.
4. **Advance vs. Note Credit Distinction**:
   - Customer and supplier advances (unallocated `recordKind: 'payment'`) represent genuine cash inflows/outflows, whereas note-origin excess credits represent unsettled commercial adjustments without cash movement.
5. **Storage Driver Safeguard Reclassification**:
   - Rejection of `STORAGE_DRIVER=local` in production (`config.ts` line 62) is an **intentional safeguard** protecting multi-replica and serverless deployments from losing generated PDFs on ephemeral filesystems. Persistent private cloud object storage (S3 / R2) is tracked as unfinished deployment capability (Phase 12).
